AI（Claude Code）に、ブログの運用を任せています。その中に、**公開前の原稿を一時的に自分のサイトに置く**工程があります。

置いたファイルは、使い終わったら消して、もう一度デプロイします。そのあと、本番のURLで404になることまで確かめていました。手順書にもそう書いてあり、毎回そのとおりにやっていました。

2026年10月12日、それでも**消したはずの原稿が、別のURLからまだ読める**ことに気づきました。Cloudflare Pages は、デプロイのたびに固有のURLを発行します。そのURLは、あとから新しいデプロイを出しても、当時の中身を返し続けます。

この記事は、何が残っていて、どう確かめ、どう直したかの記録です。

## 何をしていたか

note（ブログサービス）の記事を予約投稿する作業を、ブラウザ操作でAIに任せています。note の編集画面に本文を流し込むとき、本文のHTMLをブラウザ側のスクリプトから取りに行かせる必要がありました。その受け渡しに、自分の静的サイト（Cloudflare Pages）を使っていました。

手順はこうです。

1. 本文をHTMLにして、`public/transfer/<ランダムな16桁>.html` に置く
2. `wrangler pages deploy` でデプロイする
3. note の編集画面から、そのURLを `fetch` して本文を貼る
4. 貼り終わったら、`public/transfer/` のファイルを消して、もう一度デプロイする
5. 本番のURLで、そのファイルが404になることを確かめる

ファイル名はランダムで、どこからもリンクしていません。5番の確認もしています。これで「公開前の原稿は外から読めない」と考えていました。

## 何が残っていたか

10月12日の0時台、3本の記事を予約したあと、手順どおり配信用の3ファイルを消して再デプロイしました。本番のURLでは3つとも404でした。

そのあと、ふと `wrangler pages deployment list` を開きました。デプロイの一覧には、1件ごとに `https://<ハッシュ>.<プロジェクト名>.pages.dev` というURLが並んでいます。

このうち、**配信用ファイルを置いていた時に作ったデプロイ**のURLで、同じパスを開いてみました。

```bash
curl -sL -o /tmp/t.out -w "%{http_code}\n" \
  "https://<ハッシュ>.<プロジェクト名>.pages.dev/transfer/<ファイル名>.html"
# → 200
grep -c "<その記事にしかない言葉>" /tmp/t.out
# → 1
```

**200が返り、中身は公開前の原稿の本文そのものでした。** 本番のURLでは消えていても、その時点のデプロイを指すURLでは、当時のファイルがそのまま配信されていました。

## これは仕様どおりの動き

Cloudflare の公式ドキュメント（プレビューデプロイのページ）には、こう書かれています。

> These are atomic and may always be visited in the future.

（出典: https://developers.cloudflare.com/pages/configuration/preview-deployments/ 、2026-10-12 確認）

デプロイは1つずつ独立した「その時点の丸ごとの写し」で、あとからいつでも訪れることができる、という意味です。ロールバック（以前のデプロイに戻す機能）が成り立つのも、古いデプロイが中身ごと残っているからです。

ドキュメントのこの一文はプレビューデプロイについての説明です。ただ、私のプロジェクトは全部 `main` ブランチからの本番（Production）デプロイで、一覧を見ると、本番デプロイにも1件ずつハッシュ付きのURLが振られていました。実際に200が返ったのも、本番デプロイのURLです。

つまり、

- **本番のURL**（`<プロジェクト名>.pages.dev`）は、いつも最新のデプロイを指す
- **ハッシュ付きのURL**は、作られた時点のデプロイを指したまま動かない

ということです。消して再デプロイしても、変わるのは前者だけでした。

## どこまで残っているかを数えた

まず、手元から確かめられる範囲を全部見ました。`wrangler pages deployment list --json` で一覧を取り、各デプロイのURLに、今回の3ファイルのパスを問い合わせます。

```python
import json, urllib.request

deps = json.load(open("/tmp/deps.json"))   # wrangler pages deployment list --json の出力
names = ["<ファイル1>", "<ファイル2>", "<ファイル3>"]

for d in deps:
    row = []
    for n in names:
        url = f'{d["Deployment"]}/transfer/{n}'
        try:
            r = urllib.request.urlopen(
                urllib.request.Request(url, headers={"User-Agent": "Mozilla/5.0"}),
                timeout=15)
            row.append(r.status)
        except Exception as e:
            row.append(getattr(e, "code", "err"))
    print(d["Id"][:8], d["Status"], row)
```

`list` の一覧に出てきたデプロイは25件でした（これが全件かどうかは確かめていません）。**3ファイルが200を返したのは、そのうち1件だけ**でした。ファイルを置いてから消すまでの間に作ったデプロイです。それより前と後のデプロイでは、3つとも404でした。

ファイルが残るのは「置いていた間に作ったデプロイ」に限られる、ということです。考えてみれば当たり前ですが、数えて確かめるまでは「全部のデプロイに残っているのでは」と心配していました。

### 確かめられなかったこと

この配信の仕組みは、10月8日と9日にも使っています。そのとき置いたファイルの名前は、どこにも記録していませんでした。ランダムな名前だったので、名前が分からないと問い合わせようがありません。

その時期のデプロイにも、当時の原稿が残っていると見ています。ただし、これは推測で、確認はできていません。

1つのデプロイにどんなファイルが入っているかを一覧で出す方法は、今回は見つけられませんでした。`wrangler pages deployment` のサブコマンドは `list`・`create`・`tail`・`delete` の4つで（wrangler 4.149.0 の `--help` で確認）、中身の一覧を出すものはありません。

## なぜ気づけなかったか

手順の5番、「本番のURLで404になることを確かめる」は、毎回やっていました。**確認の手順そのものはあったのに、確認する場所が1か所だけでした。**

前に、同じ配信用ファイルが消えていなかった事故を起こしています。シェルの変数がスペースで分かれず、削除のコマンドが1つもファイルを消していなかった件です。そのときは、この404の確認で気づけました。404の確認は、確かに役に立っていました。

ただ、404の確認が言えるのは「本番のURLから消えた」ことだけです。「どこからも読めない」ことまでは言えません。私は、この2つを同じものとして扱っていました。

## 細かいところで、2つ引っかかった

### 1. `.html` なしのURLは308で転送される

本番のURLで確かめたとき、3ファイルのうち1つが404ではなく **308** を返しました。`/foo.html` へのアクセスが `/foo` へ転送されていました。転送先まで追わないと、本当の結果が分かりません。

```bash
curl -sL -o /dev/null -w "%{http_code}\n" "https://.../transfer/<ファイル名>.html"
```

`-L` を付けて転送を追うと、そのファイルは404でした。308は「消えていない」という意味ではなく、転送の途中だっただけです。逆に、ハッシュ付きのURLで原稿が見つかったときも、最初に返ってきたのは308で、追った先が200でした。**転送を追わずに数字だけ見ると、どちらの向きにも読み違えます。**

### 2. 再デプロイの直後は、古い写しが返ることがある

再デプロイの直後に確かめたら、別の1つが200を返し、中身も原稿のままでした（本番のURLです）。少しおいて問い合わせ直すと404になりました。配信網に古い写しが少しの間残っていたのだと思います（推測です）。

そのため今は、全部が404になるまで、10秒おきに問い合わせ直すようにしています。

```bash
for i in $(seq 1 30); do
  n=0
  for u in "/transfer/a.html" "/transfer/a"; do
    c=$(curl -sL -o /dev/null -w "%{http_code}" "https://<プロジェクト名>.pages.dev$u?v=$RANDOM")
    [ "$c" = "404" ] || n=$((n+1))
  done
  echo "try $i non404=$n"
  [ $n -eq 0 ] && break
  sleep 10
done
```

URLの末尾に `?v=$RANDOM` を付けているのは、手元や途中の写しを避けるためです。

## どう直したか

### 公開サイトを経由させるのをやめた

いちばん確実なのは、**消す必要のあるものを、そもそも公開の場所に置かない**ことでした。

本文の受け渡しに公開サイトを使っていたのは、ブラウザ側のスクリプトが本文を取りに行く先が必要だったからです。ところが、今回の3本の本文をHTMLにすると、1本あたり3.9KB〜4.9KBでした。これなら、ブラウザで実行するスクリプトの中に、本文を文字列として直接埋め込んで渡せます。

```javascript
// これまで: 公開サイトに置いたファイルを取りに行く
const html = await (await fetch('https://<プロジェクト名>.pages.dev/transfer/<ファイル名>.html')).text();

// 次から: スクリプトに本文を直接埋め込む（公開サイトを通らない）
const html = "<p>本文…</p><h2>…</h2>…";
view.pasteHTML(html);
```

次の予約からは、こちらに切り替えると決めました。この記事を書いた時点では、まだこの方式で1本も貼っていません。うまくいかなかった場合は、そのことも書きます。

置かなければ、消し忘れも、デプロイに残る心配もありません。

### 古いデプロイを消す方法はある

すでに残ってしまったものは、デプロイごと消せます。wrangler に `pages deployment delete` があります。

```bash
npx wrangler pages deployment delete <デプロイのID> --project-name <プロジェクト名>
```

公式のコマンドリファレンスでは、現在エイリアスが付いているデプロイ（本番として配信中のもの）を消すには `--force` が要る、とされています（出典: https://developers.cloudflare.com/workers/wrangler/commands/pages/ 、2026-10-12 確認）。

ただし、消したデプロイには、もうロールバックできません。私は、どのデプロイを消すかを運営の判断として分けて扱うことにして、今回はまだ消していません。

### プレビューをアクセス制限で守る方法もある

Cloudflare には、プロジェクトの設定で「Enable access policy」を有効にすると、プレビューデプロイに認証をかけられる機能があります。ただし、ドキュメントには「プレビューデプロイだけを守る」とあります。私のように本番デプロイのハッシュURLに残っている場合も守られるのかは、確かめていません。

## ほかの使い方でも起きうること

今回残っていたのは、数日後に公開する予定の自分の原稿でした。個人情報や認証情報は入っていません。

ただ、同じ仕組みは、公開ディレクトリに入ったものすべてに当てはまります。たとえば、APIキーの入った設定ファイルを `public/` に入れたままデプロイしてしまったとします。気づいて消し、再デプロイして本番のURLで404を確かめても、**そのときのデプロイのURLには残ります**。

この場合に必要なのは、ファイルを消すことより先に、**キーそのものを無効にして作り直すこと**だと考えています。「消した」ではなく「もう使えない」状態にしないと、残った写しから読まれたときに防げません。

## 持ち帰れる形にすると

今回から決めたことは4つです。

1. **消す前提のものは、公開ディレクトリに置かない。** 置かなければ、残らない
2. **404の確認は、本番のURLだけでなく、そのファイルを置いていた間のデプロイのURLでも行う**
3. **確認は転送を追い（`curl -L`）、全部が404になるまで繰り返す**
4. **公開してはいけないものを出してしまったら、消すより先に無効にする**

AIに頼むときは、この形で渡しています。

```
公開前の文章や設定値を、一時的にでも公開サイトのディレクトリに置かないでください。
受け渡しが必要なら、実行するスクリプトに直接埋め込んでください。

もし公開サイトに置いたものを消す場合は、本番のURLだけでなく、
置いていた間に作ったデプロイ固有のURLでも404になるかを確かめてください。
確かめられない場所が残ったら、「確かめられなかった」と報告してください。
```

最後の一文を入れているのは、今回、私が10月8日と9日の分を確かめられなかったように、**確かめられない場所は残ります**。それを「消えました」の一言にまとめさせないことが大事でした。
