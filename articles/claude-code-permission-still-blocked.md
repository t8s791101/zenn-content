Claude Code の権限モードを `bypassPermissions`（すべて許可）にして、許可ルールも100件入れた状態で、**それでも実行が拒否される操作**がありました。

拒否のメッセージはこれです。

```
Permission for this action was denied by the Claude Code auto mode classifier.
Reason: Blocked by classifier.
```

権限設定の話だと思って半日調べたので、分かったことを書きます。

## 権限モードと、その先にあるチェックは別

整理するとこうなっていました。

| | 何を見るか | 変えられるか |
|---|---|---|
| 権限モード・許可ルール | **どのツールを使ってよいか** | 設定で変えられる |
| 自動モードの安全チェック | **その操作が何をしようとしているか** | 設定では変えられない |

`bypassPermissions` が効くのは1段目だけです。2段目は、ツールの使用許可とは別の観点で見ています。だから「全部許可したのに拒否される」が起きます。

**設定ファイルをいくら見ても原因は出てきません。** ここで時間を使いました。

## 実際に止まった操作

止まったのは、外部サービス上で他人のアカウントに向けて反応を送る操作でした。もうひとつ、別のセッションを停止する操作も一度拒否されました（後日、同じ操作が通ったので、毎回同じ結果とは限りません）。

拒否の文面には、こう書かれています。

> 他に依存しないタスクがあれば、そちらを進めてください。
> 別の手段で同じことを達成しようとしてもよいですが、**拒否の意図を回避するような方法は取らないでください。**

## 迂回しようとして、やめた

最初に考えたのは次の2つです。どちらもやめました。

1. ページ側の確認ダイアログを差し替えて、確認そのものを消す
2. 別のセッションに同じ作業を頼む

1は、拒否されている操作の中身は変えずに、止めている仕組みだけを外す行為です。2は、拒否された操作を別の実行主体に移すだけで、**権限のロンダリング**にあたります。どちらも「拒否の意図を回避する方法」そのものでした。

自動化を進めていると、**止まったものを通すこと自体が目的になりがち**です。ここは分けて考えるべきところでした。

## 運用としてどうしたか

手順書に、こう書きました。

> 操作が拒否されたら**迂回しない**。`ok=0` で記録して次へ進む。

大事なのは後半です。**拒否された事実を記録に残す**。これをしないと、次の日に同じ操作を試して、また同じ場所で止まります。実際、記録を始める前は3日続けて同じところで止めていました。

記録は1行で足りました。

```sql
INSERT INTO daily_actions (done_on, action, result, ok)
VALUES ('2026-09-20', '他クリエイターへの反応', '自動モードの安全チェックで拒否', 0);
```

## まとめ

- 権限モードを最大にしても、**別の層で止まる操作がある**
- 設定を疑う前に、**拒否メッセージが何を指しているかを読む**。今回は「classifier」と明記されていた
- 止まった操作は、通そうとせず**記録して次へ回す**。人がやるべき作業として切り出す

自動化の設計では「止まらないこと」を目標にしがちですが、**止まった場所が分かることのほうが先**でした。
