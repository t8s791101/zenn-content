AI（Claude Code）に、note の記事編集を任せています。2026年10月11日、公開済みの22本で、本文の1行目だけを直しました。

直したかったのは、記事の書き出しです。22本とも、本文の1行目が「無料記事 ／ 想定読了 5分」のような定型文でした。有料の2本は「有料記事 1,280円 ／ 想定読了 20分」です。記事一覧や検索結果の抜粋は本文の頭から取られるので、**どの記事も同じ定型文から表示されていました。**

やることは単純です。1行目の定型文を、本題の段落より後ろへ下げるだけです。ただ、このやり方を決めるまでに、一度ヒヤリとしています。全文を貼り替えたら、**有料記事の有料ラインが先頭に戻っていた**ことがあるからです。

この記事は、全文の貼り替えをやめて**ブロックを1つだけ動かす**方式に切り替え、22本を直した記録です。最後に、移動の前後で何を照合したかも載せます。

## 前提: noteのエディタはProseMirror

note の編集画面は ProseMirror で動いています。画面に見えている本文の裏に `EditorView` があり、本文は「ブロック（段落・見出し・区切り線・目次など）の並び」として持たれています。

`EditorView` の取り出し方は前に書いたので、ここでは省きます（[noteの本文編集を自動化しようとして2回事故った話](https://zenn.dev/zeroyen_dev/articles/note-prosemirror-safe-replace)）。React の fiber をたどって `state` と `dispatch` を持つオブジェクトを探す方式です。以下のコードでは、それを `getView()` と書きます。

## 全文を貼り替えると、有料ラインが先頭に戻った

10月5日、有料記事（1,480円）の冒頭を直そうとしました。そのときは、本文を全部消して、直したHTMLを貼り直す方式を使いました。

```javascript
const v = getView();
v.dispatch(v.state.tr.delete(0, v.state.doc.content.size));
v.pasteHTML(html);
```

貼ったあとのエディタは正しく見えました。文字数・見出しの数・目次の数は、どれも貼る前と同じです。

ところが、「公開に進む」から「有料エリア設定」を開くと、**有料ラインが1段落目の直後に移動していました。**

```
タイトル
AI（Claude Code）に開発と運用を任せて…   ← 1段落目
このラインより先を有料にする              ← ここに移動していた
有料記事 1,480円 ／ 想定読了 20分 …
```

このまま「更新する」を押していたら、無料で読めるはずの1,358字が、ほぼ全部有料の内側に入っていました。押す前に気づいたので、キャンセルで抜けています。キャンセル後に公開中の記事を確かめると、価格・無料部分の文字数・末尾の文は、すべて変更前のままでした。

### 有料ラインはブロックのIDを指している

公開APIで記事を取ると、`separator` という項目があります。値はUUIDです。

```
GET https://note.com/api/v3/notes/<記事のキー>
→ data.separator = "xxxxxxxx-xxxx-xxxx-xxxx-xxxxxxxxxxxx"
```

この形式は、本文の各ブロックが持っている `id` と同じです。**有料ラインは「このIDのブロックの後ろ」という形で位置を持っている**と見ています。

全文を貼り替えると、ブロックは全部作り直されます。そのとき、元のブロックの `id` がそのまま残るとは限りません。ラインが先頭に戻ったのは、指していたブロックを見失ったからだと考えています。ただし、これは推測です。note側の実装は確認していません。

確実に言えるのは、**全文の貼り替えは、エディタ上の見た目が同じでも、有料ラインの位置を壊すことがある**という観測だけです。

## ブロックを1つだけ動かす

そこで、本文を作り直すのをやめました。動かしたいブロックだけを消して、別の位置に入れ直します。

```javascript
const v = getView();
const doc = v.state.doc;

const meta = doc.child(0);              // 1行目の定型文
const target = doc.child(1);            // この段落の後ろへ下げたい
const afterTarget = meta.nodeSize + target.nodeSize;

let tr = v.state.tr;
tr.delete(0, meta.nodeSize);            // 先頭のブロックを消す
tr.insert(tr.mapping.map(afterTarget), meta);  // 位置を補正して入れ直す
v.dispatch(tr);
```

要点は `tr.mapping.map()` です。

`afterTarget` は、**消す前の**文書での位置です。先頭のブロックを消すと、後ろの位置は全部その分だけ前にずれます。`tr.mapping.map()` は、同じトランザクションの中でそれまでに行った変更を踏まえて、古い位置を新しい位置に読み替えてくれます。自分で `afterTarget - meta.nodeSize` と引き算しても同じ結果になりますが、手順が増えたときに計算を間違えないよう、ずらす計算はライブラリに任せています。

入れ直しているのは、元の文書から取り出した `meta` そのものです。ノードの属性（`attrs`）もそのまま付いていくので、**ブロックの `id` は動かしたあとも同じ**でした。実際に、有料記事で動かしたあとの先頭6ブロックを出すと、`id` は動かす前と一致していました。

```
0 paragraph       39a233ed-… | コピーしてすぐ使える指示テンプレートが12種類…
1 paragraph       9b1ab0db-… | 有料記事 1,280円 ／ 想定読了 20分
2 tableOfContents 30ab3f1f-… |
3 horizontalRule  3cb47c31-… |
4 heading         c3401b27-… | この記事で手に入るもの
```

ほかのブロックには一切触れていません。有料ラインが指しているブロックも、そのまま残ります。

## 動かす前と後で、4つの数を比べる

ブロックを動かすだけなら、本文の量は変わらないはずです。そこで、動かす前と後で次の4つを数えて、1つでも違えば止めるようにしました。

```javascript
const pm = document.querySelector('.ProseMirror');
const snap = () => ({
  blocks: v.state.doc.childCount,                       // ブロック数
  len:    pm.innerText.length,                          // 表示されている文字数
  h2:     pm.querySelectorAll('h2').length,             // 見出しの数
  toc:    pm.querySelectorAll('table-of-contents').length, // 目次の数
});

const before = snap();
// …ブロックを動かす…
await new Promise(r => setTimeout(r, 1000));
const after = snap();
if (JSON.stringify(before) !== JSON.stringify(after)) {
  throw new Error('changed ' + JSON.stringify(before) + JSON.stringify(after));
}
```

この4つを選んだ理由は、**どれも「移動」では変わらず、「事故」では変わる**からです。

- 貼り付けが追記になって本文が二重になれば、`blocks` と `len` と `h2` が倍になります（前に一度やっています）
- 目次ブロックが消えれば、`toc` が減ります
- 段落が1つ消えれば、`blocks` と `len` が減ります

文字数には、エディタの右上に出る表示ではなく `innerText.length` を使いました。前後で同じ物差しを使えば足りるからです。物差しを途中で変えると、変わっていないものが変わったように見えます。

もう1つ、**先頭が本当に定型文だったか**も、動かす前に確かめています。

```javascript
if (!/^無料記事/.test(doc.child(0).textContent)) return 'skip: not meta';
```

これがないと、すでに直した記事でもう一度走らせたとき、本題の段落を後ろへ下げてしまいます。

## 1本目で止まった: 区切り線が挟まっていた

最初の1本は、スクリプトが何もせずに終わりました。

理由は、定型文の直後が段落ではなく**区切り線（`horizontalRule`）**だったことです。「定型文を、次の段落の後ろへ」という前提が崩れていました。区切り線の後ろに定型文を入れると、「区切り線 → 定型文 → 本題」という、かえって読みにくい並びになります。

そこで、直後が区切り線なら、**定型文と区切り線を2つまとめて**動かすようにしました。

```javascript
let take = 1;
if (doc.child(1).type.name === 'horizontalRule') take = 2;

const target = doc.child(take);
if (target.type.name !== 'paragraph') return 'skip: target ' + target.type.name;

let end = 0;
for (let i = 0; i < take; i++) end += doc.child(i).nodeSize;
const moved = doc.slice(0, end).content;   // 先頭からtake個ぶん
const afterTarget = end + target.nodeSize;

let tr = v.state.tr;
tr.delete(0, end);
tr.insert(tr.mapping.map(afterTarget), moved);
v.dispatch(tr);
```

`doc.slice(0, end).content` で、先頭から複数のブロックをまとめて取り出せます。`tr.insert` は `Fragment` も受け取るので、入れ直すときも1回で済みます。

移動先が段落でなければ（見出しや目次なら）、何もせずに止まります。無料の20本のうち、17本は直後が段落、3本は区切り線でした。

## 有料記事は、向きを逆にした

有料の2本は、定型文の直後が「目次 → 区切り線 → 見出し（この記事で手に入るもの）」の順でした。定型文を下げる先の段落が、近くにありません。

そこで向きを逆にしました。**見出しの下にある最初の段落を、先頭へ上げる**ことにしました。動かすブロックは1つだけで、有料ラインからは離れた場所です。

```javascript
const n = doc.child(4);   // 「この記事で手に入るもの」の下の段落
if (!/^コピーしてすぐ使える/.test(n.textContent)) throw new Error('unexpected');

let pos = 0;
for (let i = 0; i < 4; i++) pos += doc.child(i).nodeSize;

let tr = v.state.tr;
tr.delete(pos, pos + n.nodeSize);
tr.insert(0, n);
v.dispatch(tr);
```

位置を `child(4)` と決め打ちにしているので、**動かす段落の書き出しを必ず照合**しています。記事が違えば、ここで止まります。

### 「有料エリア設定」で、ラインの前後の文を読む

有料記事は、更新する前に必ず「有料エリア設定」を開きます。ここには「ラインをこの場所に変更」ボタンが、ブロックの数だけ並びます。1,280円の記事では、ブロック106個に対してボタンが105個でした。1個足りない場所に、いまのラインがあります。

ボタンの並びから位置を割り出すより、**ラインの文言の前後を読む**ほうが確実でした。

```javascript
const btns = Array.from(document.querySelectorAll('button'))
  .filter(b => b.textContent.includes('ラインをこの場所に変更'));
let p = btns[0];
while (p && !p.contains(btns[5])) p = p.parentElement;   // ボタンを全部含む親

const t = p.innerText;
const k = t.indexOf('このラインより先を有料にする');
t.slice(k - 150, k + 60);
```

出てきた前後の文が、変更前に公開APIで取っておいた「無料部分の末尾の文」と同じであることを確かめてから、「更新する」を押しました。

## 公開APIで、22本すべてを照合した

画面上で正しく見えても、保存されたものが同じとは限りません。前に「保存しました」と出たのに保存されていなかったことがあるので、最後は必ず公開APIで確かめています。

```python
import json, re, html, urllib.request

def fetch(key):
    req = urllib.request.Request(f"https://note.com/api/v3/notes/{key}",
                                 headers={"User-Agent": "Mozilla/5.0"})
    return json.load(urllib.request.urlopen(req))["data"]

for key in keys:
    d = fetch(key)
    body = d["body"]
    text = html.unescape(re.sub(r"<[^>]+>", "\n", body))
    first = next(l.strip() for l in text.split("\n") if l.strip())
    ok = (body.count("<h2") == before[key]["h2"]
          and body.count("<table-of-contents") == before[key]["toc"]
          and not re.match(r"(無料記事|有料記事)", first))
    print("OK" if ok else "NG", key, first[:24])
```

結果は22本すべて `OK` でした。見出しの数と目次の数が変更前と同じで、1行目が定型文ではありません。

有料の2本は、さらに次の3つを変更前と比べました。

| | 1,280円の記事 | 980円の記事 |
|---|---|---|
| 価格 | 1,280 → **1,280** | 980 → **980** |
| `separator`（有料ラインのID） | **変化なし** | **変化なし** |
| 無料で読める部分の文字数 | 1,274字 → **1,274字** | 1,021字 → **1,021字** |

無料部分の文字数は、ログインしていない状態で公開APIが返す本文から、タグを除いて数えています。購入していない人に見える量そのものです。

### タグの数も数えた

もう1つ、全22本で**タグの数**を変更前と比べました。以前、記事を「更新」しただけで、付けていた企画（お題）のタグが外れたことがあるからです。見た目は無事で、どこにもエラーは出ませんでした。

今回は22本とも、タグの数は変更前と同じでした。

## 同じ日に引っかかった、小さなこと

### 1. ボタンの文言が完全一致しない

見出し画像を差し替える途中で、「画像をアップロード」ボタンが見つからずに止まりました。メニューは開いていました。

原因は、ボタンの中に「推奨サイズ：1280x670px」という小さな文字も入っていたことです。`textContent.trim() === '画像をアップロード'` では一致しません。`startsWith` に変えて通りました。

### 2. 裏のタブは、スクリーンショットを撮るまで描画が止まる

ページを開いた直後、座標でのクリックが何も起こさないことが続きました。クリックの前にそのタブのスクリーンショットを1回撮ると、通るようになりました。裏に回っているタブは描画が止まっていて、撮ると進むようです。理由は確かめていません。

### 3. 切り抜き枠が小さく見えても、保存された画像は欠けていなかった

見出し画像の切り抜き画面で、枠が画像より一回り小さく表示されたことがありました。DOMで測ると、画像が718×376pxに対して、枠は646×338pxです。このまま保存すると端が切れるように見えます。

保存したあと、配信されている画像を取得して確かめると、1280×670pxで、端まで欠けずに入っていました。**画面の枠の表示と、保存される範囲は一致していませんでした。** 画面を見て判断していたら、正しく保存されるものを何度もやり直していたと思います。

## 持ち帰れる形にすると

公開中の記事を機械的に直すときに、今回守ったことはこの5つです。

1. **全文を作り直さない。** 動かすブロックだけを消して入れ直す
2. **移動の前後で、移動では変わらない数を比べる。** 違ったら保存せずに止める
3. **動かす前に、それが本当に動かすべきものかを照合する。** 2回目に走らせても壊れないようにする
4. **有料記事は、ラインの前後の文を読んでから更新する**
5. **保存されたものは、編集画面ではなく公開APIで確かめる**

AIに頼むときは、この形で渡しています。

```
公開中の記事の一部を直すときは、本文全体を貼り替えないでください。
動かすブロックだけを消して、別の位置に入れ直してください。

動かす前と後で、ブロック数・文字数・見出しの数・目次の数を数え、
1つでも違えば保存せずに止めてください。

有料記事は、更新を押す前に「有料エリア設定」を開き、
ラインの前後の文が変更前と同じかを確かめてください。

保存したあとは、公開APIで本文を取り直し、
変更前と同じであるべき数が同じかを確かめてから、完了と報告してください。
```

全文の貼り替えは、1行で書けて楽です。そのぶん、何が変わったかが見えません。ブロックを1つだけ動かすやり方は、書く量は増えますが、**変わったものが1つだけだと言える**ようになりました。
