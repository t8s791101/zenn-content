AI（Claude Code）に、ブログの運用そのものを1か月任せました。記事を書く、数字を測る、サイトを直す、定期実行を組む。コードを書かせるのではなく、**作業を回させる**使い方です。

結果として、**止まった場所が偏っている**ことが分かりました。コードの誤りではほとんど止まりません。止まるのはいつも、その手前か、その外側です。

この記事は、1か月で実際に止まった場所の地図です。再現手順と、こちらで取った数字を全部出します。**きれいな結論は出ていません。** 分かっていないことは、分かっていないと書きます。

## 前提：何を任せたか

| 対象 | 内容 |
|---|---|
| 記事 | 下書きの作成、公開予約、タイトルと本文の修正 |
| 数字 | 毎日のPV取得、データベースへの記録、ダッシュボードへの反映 |
| サイト | 静的サイトの修正とデプロイ（Cloudflare Pages） |
| 定期実行 | 毎朝の処理をスケジュールタスクとWorkerのcronで |

期間は約1か月。費用は0円（無料枠だけ）。環境はmacOS + Claude Code。

## 1. いちばん多いのは「成功と報告されたのに、できていない」

これが一番多く、一番気づきにくいところでした。

### 事例：8日間、止まっていたことに気づかなかった

毎日1回の定期実行を `launchd` で組みました。**8日間、一度も動いていませんでした。**

- エラー通知: ゼロ
- ログファイル: 0バイト
- `launchctl list`: ちゃんと載っている
- **手でシェルから実行すると成功する**

原因はスクリプトの置き場所でした。iCloud Driveの中に置いていて、実体がクラウドにしか無い状態だと、`launchd` から起動できません。手で叩くと、Finderが実体を落としてくるので成功します。**テストでは絶対に気づけない形**でした。

### 事例：デプロイ成功なのに、公開されていない

デプロイのコマンドは成功で終わり、AIも「公開しました」と報告しました。公開URLを開くと、古い内容のままでした。

### 事例：画像を「設定しました」、実物には無い

記事の見出し画像を設定させました。報告は成功。APIで記事を取り直すと、画像の項目が空でした。挿入の操作はしていて、**最後の「保存」を押していませんでした。**

### 共通していること

**どれも、AIが嘘をついたわけではありません。** 操作は実行されています。ただ、操作の完了と、結果の反映が一致していませんでした。

AIは「自分が実行したこと」は知っていますが、「実行の結果どうなったか」は、見に行かないと知りません。そして、見に行けとは言われていませんでした。

### 効いた対策：報告の代わりに実物を出させる

指示の末尾に、この一文を足しました。

```
設定・公開・投稿をしたら、その報告の代わりに、
実物（公開されたデータ、投稿の一覧、成果物の件数）を取り直して、
前と後の数字を並べて報告してください。
```

これだけで、上の3件は防げるようになりました。報告は「成功」でした。実物は違いました。**確認の対象を、報告から実物に移すだけ**です。

## 2. 数え方を間違える（同じ形で4回踏んだ）

APIからデータを取って集計する処理で、**同じ間違いを4回しました。** 全部「ページが分かれているAPIを、1ページ目だけ読んだ」です。

| 回 | 1ページの件数 | 起きたこと |
|---|---|---|
| 1 | 6 | 記事数を少なく数えた |
| 2 | 6 | 同上（別の用途で再発） |
| 3 | 12 | 17本中12本しか記録されず、PVの少ない記事が丸ごと抜けた |
| 4 | 5 | 7本中5本しか返らず、古い2本が消えたように見えた |

4回目は、3回目の反省を書いた後に踏みました。**同じ罠だと分かっていても、別のサービスだと気づけません。**

### なぜ気づきにくいか

エラーが出ないからです。返ってくるJSONは正常で、配列にもデータが入っています。**足りないことだけが分かりません。**

さらに悪いことに、多くのAPIは並び順がPV降順です。落ちるのは必ず「数字が小さい記事」。合計への影響が小さいので、合計値を見ていても異常に見えません。3回目のときは合計PVが183と出ていて、実際は189でした。6の差では気づけません。

### 効いた対策：件数を別の情報源と突き合わせる

ループを直すより、こちらのほうが効きました。

```
統計APIが返した件数（22） vs 公開記事数（22） → 一致
```

公開記事数は、認証の要らない別のAPIから取れます。**同じAPIの中で完結させない**のがポイントです。1ページ目だけ読んでいると、この比較で必ず引っかかります。

打ち切り条件がAPIごとに違うのも、間違えやすい理由でした。

| API | 1ページ | 打ち切りの条件 |
|---|---|---|
| A | 6件 | 空配列が返る |
| B | 12件 | `last_page: true` |
| C | 5件 | 空配列が返る |

ループは書き直すたびに間違えますが、**件数の突き合わせは1回作れば全部のAPIに効きます。**

## 3. 「変わっていないこと」を、壊れている指標で確かめていた

作業の前後で本文が壊れていないかを、**文字数**で確認していました。

ある日、記事を更新したら本文の長さが 21,101 → 20,095 に減りました。1,006字が消えたと判断して、復旧の作業に入りました。

**消えていませんでした。** このサービスは保存のたびに、各ブロックの `name` と `id` を振り直します。属性の文字数が変わるので、本文の長さは中身が同じでも動きます。実際、次の保存で 21,101 に戻りました。

### 効いた対策：動かない数字で確かめる

```
作業の結果を確認するときは、保存のたびに動く数字を使わないでください。
文章だけの文字数、見出しの数、目次の有無、リンクの一覧の4つを、
作業の前と後で取って並べてください。
```

**確認に使う数字は、変わってほしくないものだけにする。** 動く数字を見張ると、慣れて、見なくなります。

## 4. 権限を全部開けても、止まる操作がある

権限モードを「すべて許可」にして、許可ルールも100件入れた状態で、それでも拒否される操作がありました。

```
Permission for this action was denied by the auto mode classifier.
Reason: Blocked by classifier.
```

権限設定の話だと思って半日調べました。**外れでした。**

| | 何を見るか | 設定で変えられるか |
|---|---|---|
| 権限モード・許可ルール | どのツールを使ってよいか | 変えられる |
| 自動モードの安全チェック | その操作が何をしようとしているか | 変えられない |

設定ファイルをいくら見ても原因は出てきません。拒否のメッセージに `classifier` と書いてあり、そこが答えでした。**エラーの文面を読むより先に、設定を疑ってしまった**のが遅れた理由です。

### やめたこと

最初に考えた回避策は2つあり、どちらもやめました。

1. ページ側の確認ダイアログを差し替えて、確認そのものを消す
2. 別のセッションに同じ作業を頼む

1は、拒否されている操作の中身は変えずに、止めている仕組みだけを外す行為です。2は、拒否された操作を別の実行主体に移すだけで、**権限のロンダリング**にあたります。

自動化を進めていると、**止まったものを通すこと自体が目的になりがち**です。ここは分けて考えるところでした。

### 代わりに入れた決まり

```
操作が拒否されたら迂回しない。ok=0 で記録して次へ進む。
```

大事なのは後半です。**拒否された事実を記録に残す。** これをしないと、翌日また同じ場所で止まります。記録を始める前は、3日続けて同じところで止めていました。

## 5. 手順書が育ちすぎて、実行が進まなくなった

毎朝の作業手順を書いたファイルが、**30,474字**まで育ちました。踏んだ失敗とその回避策を、良かれと思って足し続けた結果です。

3日続けて、タスクが**開始の記録すら残さずに終わる**ようになりました。エラーは出ません。

原因を権限設定だと考えて、そこを1日使いました。**これも外れでした。** 設定を見たら、すでに全許可で、許可ルールが100件入っていました。

**5,503字まで削ったら、同じタスクが17分で最後まで走りました。**

| | 削る前 | 削った後 |
|---|---|---|
| 文字数 | 30,474 | **5,503** |
| 開始の記録 | 残らない | 実行から**10秒**で記録 |
| 完了まで | 3日間とも未完 | **17分で完走** |

削ったのは「経緯」と「根拠」です。**なぜその手順になったかを、別のファイルに全部移しました。** 手順書に残したのは、毎回必ず読む必要があるものだけ（判断の分岐・順番・禁止事項）です。

情報を消したわけではありません。**読むタイミングを変えただけ**です。

## 6. 定期実行そのものが、静かに止まる

これは**まだ直っていません。** 現象だけ書きます。

毎朝のタスクが、ある日から完走しなくなりました。切り分けの結果は2つに分かれました。

### (1) 時刻が来ても起動しないものがある

| タスク | 予定時刻 | 実行回数 |
|---|---|---|
| A | 09-28 12:00 | **0** |
| B | 09-30 21:00 | **0** |

有効の状態で、次回実行時刻が過去のまま、履歴が1件もありません。

### (2) 起動したものは、最初のツール呼び出しで止まる

| 実行 | 止まった場所 | 開始からの秒数 |
|---|---|---|
| 1 | — | 4秒 |
| 2 | ツール読み込みの直後 | 6秒 |
| 3 | ブラウザ操作の直後 | 39秒 |
| 4 | **最初のシェル実行の直後** | 5秒 |

4回目は、ブラウザを一切使わない手順書に書き換えた後です。**特定のツールの問題ではありません。**

止まった実行は何十時間も「実行中」のまま残り、**次の予定実行を塞ぎます。** 止めると、翌朝から動き出します。

### 分かっていること・いないこと

- スリープではない（`uptime` は連続稼働、該当時刻のログファイルがある）
- このプロジェクト固有でもない（別プロジェクトの定期実行も同じ時期に止まっている）
- **なぜ最初のツール呼び出しで止まるのかは、分かっていません**

いま分かっている対処は「止まった実行を手で止める」だけです。根本の原因は追えていません。

## 7. 「止まったこと」に気づくために入れたもの

ここまでの失敗に共通するのは、**止まったことが通知されない**点です。失敗は「失敗」として扱われず、「まだ実行中」や「成功」として静かに残ります。

入れたのは2つだけです。

### 開始と終了を、両方書かせる

```sql
INSERT INTO daily_actions (done_on, action, result, ok)
VALUES ('2026-09-25', '日次タスク開始', '開始', 1);
```

終了時にも同じように1行書きます。これで3つの状態が区別できます。

| 記録 | 意味 |
|---|---|
| 開始あり・終了あり | 完走した |
| 開始あり・終了なし | **途中で止まった** |
| 開始なし | **そもそも起動していない** |

6節の切り分けは、この2行が無ければできませんでした。

### 失敗も必ず書かせる

```
操作が拒否されたら、ok=0 で記録して次へ進む。
```

**成功だけを記録すると、記録は嘘になります。** 拒否も、取れなかった数字も、同じ重さで書く。これをやめた瞬間に、あとから何も判断できなくなります。

## 8. 1か月の数字

正直に書きます。

| | 値 |
|---|---|
| 記録した事故 | 22件 |
| うち**AIが書いたコードの誤り**が原因 | **ほぼゼロ** |
| 止まった定期実行 | 延べ6回以上（未解決） |
| 原因の見立てを外した回数 | 2回（権限だと思って半日／1日） |

**動いていました。確かめ方が足りませんでした。** これが1か月の結論です。

コードの品質を上げる話は、この1か月ではほとんど出番がありませんでした。効いたのは全部、**実行の外側**にある確認と記録でした。

## おわりに

もう一度、効いたものだけ並べます。

1. **報告の代わりに実物を出させる**（取り直して前後の数字を並べる）
2. **件数を、別の情報源と突き合わせる**（同じAPIの中で完結させない）
3. **確認には、動かない数字を使う**（保存のたびに変わるものを見張らない）
4. **拒否されたら迂回せず、記録する**
5. **手順書は育つ前提で、定期的に削る**
6. **開始と終了を両方書かせる**（止まった場所が分かるのはこれだけ）

どれも賢い仕組みではありません。全部、**確かめ方の話**です。

AIに作業を任せると、できないことより「できたと言われたのにできていないこと」のほうがずっと多い、というのが1か月の実感でした。
