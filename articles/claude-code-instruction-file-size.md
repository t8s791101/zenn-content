Claude Code に毎朝の運用作業を任せています。その手順書（スキルファイル）が **30,474字**まで育ったところで、タスクが3日続けて進まなくなりました。**5,503字に削ったら、同じタスクが17分で最後まで走りました。**

## 何が起きていたか

毎朝10時に「数字を見て、その日の改善を1つ実行し、記録する」というタスクを動かしています。手順書には、これまでに踏んだ失敗と、その回避策を足し続けていました。良かれと思って書いた注意書きが積み上がって、3万字です。

2026年9月21日から23日まで、このタスクは**開始の記録すら残さずに終わる**ようになりました。エラーは出ません。

原因を権限設定だと考えて、そこを1日調べました。**これは外れでした。** 設定を確認したら、すでに全許可の状態で、100件の許可ルールが入っていました。権限は最初から問題ではなかったのです。

## 削った結果

手順書を1画面に収まる量まで削りました。

| | 削る前 | 削った後 |
|---|---|---|
| 文字数 | 30,474 | **5,503** |
| 開始の記録 | 残らない | 実行から**10秒**で記録 |
| 完了まで | 3日間とも未完 | **17分で完走** |

削ったのは「経緯」と「根拠」です。**なぜその手順になったかを全部、別のファイル（引き継ぎメモ）に移しました。**

手順書に残したのは、この4つだけです。

1. 止まらないための約束（対話を求めるコマンドを使わない、拒否されたら迂回しない）
2. 毎日やること（順番）
3. いま走っている実験と、その判定日
4. やってよいこと／だめなこと

## 何を捨てて、何を残すか

捨てたのは、**読む必要が「いつか」しかないもの**です。

- 過去の事故の詳細な経緯
- その手順になった理由の説明
- 一度しか起きていない例外の対処

残したのは、**毎回必ず読む必要があるもの**です。判断の分岐、順番、禁止事項。

引き継ぎメモには、こう書きました。

> 詳しい手順・経緯・根拠は全部 `HANDOFF.md` にある。**必要になった時だけ読む。** ここには書かない。

情報を消したわけではありません。**読むタイミングを変えただけ**です。

## 教訓は「原因を先に測る」

いちばん効いたのは、削ったこと自体より、**原因の見立てが外れていたと認めたこと**でした。

権限だと思い込んで1日使いました。設定ファイルを実際に見れば、5分で違うと分かった話です。「たぶんこれだろう」で動く前に、**その仮説が成り立つかを1つ測る**。今回はそれをしていませんでした。

手順書が育つのは自然なことです。育ったものを定期的に測って、閾値を超えたら削る。**育つ前提で、削る作業を運用に入れておく**のが正解でした。
